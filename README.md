# Sematics-Operator

Эксперимент: можно ли использовать **временные изменения внутренних весов LLM**
как операции над представлением ситуации и её последствиями?

Первая версия обучает небольшие низкоранговые поправки к одному внутреннему
линейному слою. Затем проверяет отдельные операции, их композицию, замену
предположения и откат. Основные веса и файлы модели не перезаписываются.
Это исследовательский стенд, **не готовая рассуждающая модель и не доказательство
«голографичности» весов**.

## Установка

Python 3.11+. Команды выполняются из корня репозитория.

```bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -e '.[dev]'
```

Для GPU установите подходящую вашей системе сборку PyTorch. Первый CPU-прогон
лучше делать с небольшой моделью и `float32`.

## Путь к моделям задаётся один раз

Скопируйте `.env.example` в `.env` и укажите свою общую папку:

```dotenv
SO_MODELS_DIR=D:/Models
SO_MODEL=small
# Необязательно:
# SO_DEVICE=cuda
# SO_DTYPE=bfloat16
```

На Linux путь может быть `/home/user/models`. Относительный `SO_MODELS_DIR`
разрешается относительно `.env`. Переменные окружения процесса приоритетнее `.env`.

В `configs/experiment.toml` задайте имена подпапок и постоянные профили:

```toml
default_model = "small"

[models.small]
path = "Qwen2.5-0.5B-Instruct"
device = "auto"
dtype = "float32"
target_module = ""  # Автоматически выбирается средний MLP down projection.

[models.second]
path = "another-local-model"
device = "auto"
dtype = "float32"
target_module = ""
```

Секция `[experiment]` в поставляемом конфиге задаёт ранг, шаги, learning rate,
веса регуляризации, seed, предел длины и папку отчётов. `output_dir` разрешается
относительно TOML. Для машинных настроек можно использовать игнорируемый Git
`configs/experiment.local.toml` и `--config configs/experiment.local.toml`.

Поддерживаются **локальные Hugging Face causal LM в safetensors** и **отдельные
GGUF-файлы**. GGUF деквантуется в floating-point тензоры PyTorch: после этого доступны
градиенты, редактирование внутренних весов и точный откат. Это не запуск через LM Studio
и не обучение непосредственно в Q8_0. Исходный GGUF остаётся неизменным.

LFM2/LFM2.5 проверяется отдельными интеграционными тестами. Другие архитектуры используют
загрузчик GGUF из Transformers и ограничены его поддержкой моделей/токенизаторов.
Split-GGUF, bitsandbytes, `trust_remote_code` и несколько устройств не поддерживаются.
Загрузчик не скачивает модели. Для моделей с chat template он применяется автоматически.

### Твой LFM2.5-1.2B Q8_0 из LM Studio

После обновления зависимостей (`python -m pip install -e '.[dev]'`) достаточно `.env`:

```dotenv
SO_MODELS_DIR=C:/Users/bolthold/.lmstudio/models
SO_MODEL=lfm2_5_1_2b_gguf
```

Профиль уже добавлен в `configs/experiment.toml` и указывает на
`lmstudio-community/LFM2.5-1.2B-Instruct-GGUF/LFM2.5-1.2B-Instruct-Q8_0.gguf`.
Можно также задать абсолютный путь к `.gguf` в поле `path` своего профиля.
Внешние `config.json`/`tokenizer.json` для LFM2 GGUF не нужны: метаданные,
словарь, merges, special token IDs и шаблон чата читаются из самого файла.
Автовыбор слоя поддерживает `feed_forward.w2`.

При деквантизации 1.2B-модели только FP32-веса занимают примерно 4.8 GB;
загрузка, активации и вычисление градиентов требуют дополнительной RAM/VRAM.
`dtype = "bfloat16"` уменьшает память размещённой модели на совместимом устройстве,
но загрузчик GGUF сначала восстанавливает FP32-тензоры в RAM.
Перед загрузкой выводится оценка размера этих тензоров.

## Запуск

```bash
# Проверить загрузку и получить точные имена доступных Linear-слоёв:
semop inspect

# Первый короткий прогон — 5 шагов на каждый примитив:
semop run --steps 5

# Полный бюджет из конфига:
semop run

# Переключать модели без изменения путей или исходного кода:
semop run --model second
```

Также доступно `python -m semantics_operator run`. Если автоматический выбор слоя
не поддерживает архитектуру, укажите точное имя из `inspect` в `target_module`.
Выходная `lm_head` исключена: редактируется внутренний слой.

## Что делает эксперимент

Внешний эталон — маленькая структурная причинная модель:

```text
relay = source AND switch
lamp = relay
flag — независимое значение
```

Обучаются три примитива: `do(relay=0)`, `do(relay=1)`, `do(lamp=1)`.
Операция записывается в эффективные веса; текст вопроса в этом режиме не содержит
указания на вмешательство. Проверяются ответы про **все пять переменных**.

`W_effective = W_base + B @ A / sqrt(rank)` реализован дополнительным линейным
вычислением, математически эквивалентным изменению матрицы. Оптимизируются только
A и B. Базовые параметры заморожены. Оптимизация использует oracle-ответы на
тренировочные примеры; это supervised-поиск отдельных операторов.

Train/test содержат все 8 сочетаний входов, но разные имена устройств и формулировки.
Тест не участвует в обучении, ранней остановке или выборе лучшей поправки. Композиции
не обучаются: матрицы независимо обученных операторов складываются при проверке.
Замена предположения реализована явным правилом «последнее значение для узла»;
самостоятельное обнаружение противоречий пока не реализовано.

Для каждого сценария сравниваются:

| Режим | Где задаётся вмешательство |
|---|---|
| `base` | Нигде; исходная модель |
| `weight_edit` | Временные поправки к внутренним весам |
| `random_norm_matched` | Случайные поправки того же ранга и нормы каждой матрицы |
| `explicit_prompt` | Явное описание вмешательства в тексте, исходные веса |

Сценарии: три примитива, композиция в обоих порядках, замена `relay=0` на `relay=1`
и пустая ветвь. После удаления слоя-обёртки повторяются исходные вопросы и проверяется
неизменность исходной матрицы по SHA-256. Все forward выполняются с `use_cache=False`,
поэтому KV-cache от старых весов не переносится в новую ветвь.

## Результаты

Каждый запуск создаёт отдельную папку `runs/<timestamp>-<id>/`:

- `report.json`: конфигурация и версии, losses, нормы, исходные scores и oracle-ответы,
  accuracy по узлам, изменённым/неизменённым фактам, сохранение ранее верных ответов,
  контроль отката.
- `summary.md`: компактная таблица сравнения режимов.
- `operators.safetensors`: факторы A/B каждого оператора; метаданные слоя и хеш
  исходной матрицы. Формула восстановления: `B @ A / sqrt(A.shape[0])`.
- `representations.safetensors`: векторы выхода выбранного слоя на последнем токене
  вопроса о лампе, до/после вмешательств, по 8 тестовым устройствам в порядке датасета.

Все токены продолжений ` 0` и ` 1` учитываются в log-likelihood; нет предположения,
что число кодируется одним токеном. `p1` — вероятность **среди двух кандидатов**,
не вероятность свободной генерации. Слишком длинные входы вызывают ошибку вместо
молчаливого усечения. Пакет scoring — два вопроса, для каждого два продолжения.

Модели, `.env`, машинные конфиги и результаты игнорируются Git. Сохранённые поправки
имеют смысл только с той же исходной моделью и слоем; перенос между моделями не заявлен.

## Как интерпретировать

Одна высокая общая accuracy ничего не доказывает: её могут обеспечивать неизменившиеся
факты. Смотрите `changed`, `unchanged`, `preservation_of_correct_base_answers`, метрики
по узлам и сравнение со случайным контролем. Слабая исходная компетенция также видна
в сценарии `rollback` / `base`.

Границы исследовательского эксперимента: фиксированный простой механизм, перенос только на имена и формулировки,
один seed за запуск, три task-specific оператора. Нет проверки новых причинных графов,
длинных цепочек, универсальных операторов или автономного рассуждения. Успешный прогон
означает, что инфраструктура работает; содержательные выводы требуют pretrained-моделей,
нескольких seeds и более строгих задач. [Дизайн эксперимента](docs/design.md).

## Проверки

```bash
python -m pytest -q
```

Тесты не требуют интернета или скачивания моделей. Создают маленький случайный Llama,
проверяют загрузку с диска, градиенты, эквивалентность изменениям матрицы, композицию,
изоляцию снимков, откат после исключения и полный запуск CLI с артефактами.
Дополнительно создаются настоящие GGUF-файлы F32 и Q8_0 с гибридной LFM2
(conv + attention), проверяются значения всех восстановленных весов, logits, градиенты,
сохранение BOS/EOS, отказ при недостающих весах и полный CLI-прогон.
Случайные модели используются только для проверки кода. Пользовательский файл 1.2B
не входит в тесты и здесь не запускался.

### Покрытие обучения (v2)

Каждый шаг использует два вопроса из **train**: один, чей правильный ответ
меняется при вмешательстве, и один, чей ответ должен сохраниться. В начале
каждого цикла выбираются примеры, различающие текущий оператор и остальные
примитивы. Затем очередь проходит все оставшиеся вопросы своего пула без
повторений; меньший пул начинает новый цикл раньше. Это намеренно повышает
долю редких случаев вмешательства до 50%, меняя распределение обучения.
Тестовые вопросы и композиции при подборе не используются.

`report.json → training_sampling.operators` содержит число показов изменяемых
и сохраняемых фактов, покрытие уникальных вопросов, число различающих примеров
для каждой пары операторов и ключи вопросов каждого шага. Это проверка входных
данных обучения, а не гарантия усвоения операции. Пять шагов подходят для
проверки запуска; для первого содержательного прогона:

```console
semop run --steps 40
```

Для текущих 40 обучающих вопросов такой бюджет покрывает оба пула полностью.
Сравнивайте прежде всего `changed`, `unchanged` и сохранение ранее правильных
ответов; общая точность может расти без успешного выполнения вмешательства.
Результаты v1 и v2 используют разное распределение обучающих примеров.
