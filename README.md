# Sematics-Operator

Эксперимент: можно ли использовать **временные изменения внутренних весов LLM**
как операции над представлением ситуации и её последствиями?

Первая версия обучает небольшие низкоранговые поправки к одному внутреннему
линейному слою. Затем проверяет отдельные операции, их композицию, замену
предположения и откат. Основные веса и файлы модели не перезаписываются.
Это исследовательский стенд, **не готовая рассуждающая модель и не доказательство
«голографичности» весов**.

## Установка

Python 3.11+. Команды выполняются из корня репозитория.

```bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -e '.[dev]'
```

Для GPU установите подходящую вашей системе сборку PyTorch. Первый CPU-прогон
лучше делать с небольшой моделью и `float32`.

## Путь к моделям задаётся один раз

Скопируйте `.env.example` в `.env` и укажите свою общую папку:

```dotenv
SO_MODELS_DIR=D:/Models
SO_MODEL=small
# Необязательно:
# SO_DEVICE=cuda
# SO_DTYPE=bfloat16
```

На Linux путь может быть `/home/user/models`. Относительный `SO_MODELS_DIR`
разрешается относительно `.env`. Переменные окружения процесса приоритетнее `.env`.

В `configs/experiment.toml` задайте имена подпапок и постоянные профили:

```toml
default_model = "small"

[models.small]
path = "Qwen2.5-0.5B-Instruct"
device = "auto"
dtype = "float32"
target_module = ""  # Автоматически выбирается средний MLP down projection.

[models.second]
path = "another-local-model"
device = "auto"
dtype = "float32"
target_module = ""
```

Секция `[experiment]` в поставляемом конфиге задаёт ранг, шаги, learning rate,
веса регуляризации, seed, предел длины и папку отчётов. `output_dir` разрешается
относительно TOML. Для машинных настроек можно использовать игнорируемый Git
`configs/experiment.local.toml` и `--config configs/experiment.local.toml`.

Поддерживаются **локальные Hugging Face causal LM в safetensors** и **отдельные
GGUF-файлы**. GGUF деквантуется в floating-point тензоры PyTorch: после этого доступны
градиенты, редактирование внутренних весов и точный откат. Это не запуск через LM Studio
и не обучение непосредственно в Q8_0. Исходный GGUF остаётся неизменным.

LFM2/LFM2.5 проверяется отдельными интеграционными тестами. Другие архитектуры используют
загрузчик GGUF из Transformers и ограничены его поддержкой моделей/токенизаторов.
Split-GGUF, bitsandbytes, `trust_remote_code` и несколько устройств не поддерживаются.
Загрузчик не скачивает модели. Для моделей с chat template он применяется автоматически.

### Твой LFM2.5-1.2B Q8_0 из LM Studio

После обновления зависимостей (`python -m pip install -e '.[dev]'`) достаточно `.env`:

```dotenv
SO_MODELS_DIR=C:/Users/bolthold/.lmstudio/models
SO_MODEL=lfm2_5_1_2b_gguf
```

Профиль уже добавлен в `configs/experiment.toml` и указывает на
`lmstudio-community/LFM2.5-1.2B-Instruct-GGUF/LFM2.5-1.2B-Instruct-Q8_0.gguf`.
Можно также задать абсолютный путь к `.gguf` в поле `path` своего профиля.
Внешние `config.json`/`tokenizer.json` для LFM2 GGUF не нужны: метаданные,
словарь, merges, special token IDs и шаблон чата читаются из самого файла.
Автовыбор слоя поддерживает `feed_forward.w2`.

При деквантизации 1.2B-модели только FP32-веса занимают примерно 4.8 GB;
загрузка, активации и вычисление градиентов требуют дополнительной RAM/VRAM.
`dtype = "bfloat16"` уменьшает память размещённой модели на совместимом устройстве,
но загрузчик GGUF сначала восстанавливает FP32-тензоры в RAM.
Перед загрузкой выводится оценка размера этих тензоров.

## Запуск

```bash
# Проверить загрузку и получить точные имена доступных Linear-слоёв:
semop inspect

# Первый короткий прогон — 5 шагов на каждый примитив:
semop run --steps 5

# Полный бюджет из конфига:
semop run

# Переключать модели без изменения путей или исходного кода:
semop run --model second
```

Также доступно `python -m semantics_operator run`. Если автоматический выбор слоя
не поддерживает архитектуру, укажите точное имя из `inspect` в `target_module`.
Выходная `lm_head` исключена: редактируется внутренний слой.

## Что делает эксперимент

Внешний эталон — маленькая структурная причинная модель:

```text
relay = source AND switch
lamp = relay
flag — независимое значение
```

Обучаются три примитива: `do(relay=0)`, `do(relay=1)`, `do(lamp=1)`.
Операция записывается в эффективные веса; текст вопроса в этом режиме не содержит
указания на вмешательство. Проверяются ответы про **все пять переменных**.

`W_effective = W_base + B @ A / sqrt(rank)` реализован дополнительным линейным
вычислением, математически эквивалентным изменению матрицы. Оптимизируются только
A и B. Базовые параметры заморожены. Оптимизация использует oracle-ответы на
тренировочные примеры; это supervised-поиск отдельных операторов.

Train/test содержат все 8 сочетаний входов, но разные имена устройств и формулировки.
Тест не участвует в обучении, ранней остановке или выборе лучшей поправки. Композиции
не обучаются: матрицы независимо обученных операторов складываются при проверке.
Замена предположения реализована явным правилом «последнее значение для узла»;
самостоятельное обнаружение противоречий пока не реализовано.

Для каждого сценария сравниваются:

| Режим | Где задаётся вмешательство |
|---|---|
| `base` | Нигде; исходная модель |
| `weight_edit` | Временные поправки к внутренним весам |
| `random_norm_matched` | Случайные поправки того же ранга и нормы каждой матрицы |
| `explicit_prompt` | Явное описание вмешательства в тексте, исходные веса |

Сценарии: три примитива, композиция в обоих порядках, замена `relay=0` на `relay=1`
и пустая ветвь. После удаления слоя-обёртки повторяются исходные вопросы и проверяется
неизменность исходной матрицы по SHA-256. Все forward выполняются с `use_cache=False`,
поэтому KV-cache от старых весов не переносится в новую ветвь.

## Результаты

Каждый запуск создаёт отдельную папку `runs/<timestamp>-<id>/`:

- `report.json`: конфигурация и версии, losses, нормы, исходные scores и oracle-ответы,
  accuracy по узлам, изменённым/неизменённым фактам, сохранение ранее верных ответов,
  контроль отката.
- `summary.md`: компактная таблица сравнения режимов.
- `operators.safetensors`: факторы A/B каждого оператора; метаданные слоя и хеш
  исходной матрицы. Формула восстановления: `B @ A / sqrt(A.shape[0])`.
- `representations.safetensors`: векторы выхода выбранного слоя на последнем токене
  вопроса о лампе, до/после вмешательств, по 8 тестовым устройствам в порядке датасета.

Все токены продолжений ` 0` и ` 1` учитываются в log-likelihood; нет предположения,
что число кодируется одним токеном. `p1` — вероятность **среди двух кандидатов**,
не вероятность свободной генерации. Слишком длинные входы вызывают ошибку вместо
молчаливого усечения. Пакет scoring — два вопроса, для каждого два продолжения.

Модели, `.env`, машинные конфиги и результаты игнорируются Git. Сохранённые поправки
имеют смысл только с той же исходной моделью и слоем; перенос между моделями не заявлен.

## Как интерпретировать

Одна высокая общая accuracy ничего не доказывает: её могут обеспечивать неизменившиеся
факты. Смотрите `changed`, `unchanged`, `preservation_of_correct_base_answers`, метрики
по узлам и сравнение со случайным контролем. Слабая исходная компетенция также видна
в сценарии `rollback` / `base`.

Границы исследовательского эксперимента: фиксированный простой механизм, перенос только на имена и формулировки,
один seed за запуск, три task-specific оператора. Нет проверки новых причинных графов,
длинных цепочек, универсальных операторов или автономного рассуждения. Успешный прогон
означает, что инфраструктура работает; содержательные выводы требуют pretrained-моделей,
нескольких seeds и более строгих задач. [Дизайн эксперимента](docs/design.md).

## Проверки

```bash
python -m pytest -q
```

Тесты не требуют интернета или скачивания моделей. Создают маленький случайный Llama,
проверяют загрузку с диска, градиенты, эквивалентность изменениям матрицы, композицию,
изоляцию снимков, откат после исключения и полный запуск CLI с артефактами.
Дополнительно создаются настоящие GGUF-файлы F32 и Q8_0 с гибридной LFM2
(conv + attention), проверяются значения всех восстановленных весов, logits, градиенты,
сохранение BOS/EOS, отказ при недостающих весах и полный CLI-прогон.
Случайные модели используются только для проверки кода. Пользовательский файл 1.2B
не входит в тесты и здесь не запускался.

### Покрытие обучения (v2)

Каждый шаг использует два вопроса из **train**: один, чей правильный ответ
меняется при вмешательстве, и один, чей ответ должен сохраниться. В начале
каждого цикла выбираются примеры, различающие текущий оператор и остальные
примитивы. Затем очередь проходит все оставшиеся вопросы своего пула без
повторений; меньший пул начинает новый цикл раньше. Это намеренно повышает
долю редких случаев вмешательства до 50%, меняя распределение обучения.
Тестовые вопросы и композиции при подборе не используются.

`report.json → training_sampling.operators` содержит число показов изменяемых
и сохраняемых фактов, покрытие уникальных вопросов, число различающих примеров
для каждой пары операторов и ключи вопросов каждого шага. Это проверка входных
данных обучения, а не гарантия усвоения операции. Пять шагов подходят для
проверки запуска; для первого содержательного прогона:

```console
semop run --steps 40
```

Для текущих 40 обучающих вопросов такой бюджет покрывает оба пула полностью.
Сравнивайте прежде всего `changed`, `unchanged` и сохранение ранее правильных
ответов; общая точность может расти без успешного выполнения вмешательства.
Результаты v1 и v2 используют разное распределение обучающих примеров.

### Контрастные векторы активаций

```console
semop steer
```

Команда использует ту же модель и `.env`. Для каждого внутреннего MLP-выхода
она извлекает среднюю разность активаций между парными train-промптами:
явное вмешательство (`relay=0`, `relay=1`, `lamp=1`) минус исходная ситуация.
Снимается последний токен промпта, до ответа. Это адаптация идеи
[Persona Vectors](https://github.com/safety-research/persona_vectors), а не
воспроизведение усреднения по токенам ответа из статьи.

Слой и коэффициент выбираются по отдельной validation-формулировке и именам.
Цель выбора: сначала доля полностью правильных ситуаций (все пять узлов),
затем правильность пары реле–лампа, затем общая точность. Нулевой коэффициент
всегда включён; при равенстве внутри слоя предпочитается меньшая абсолютная
сила. Train/validation/test имеют одинаковую таблицу истинности, поэтому это
ограниченная проверка переноса формулировок, а не новых механизмов.

Быстрый первый запуск для LFM2 (один слой, короткая сетка):

```console
semop steer --layers model.layers.8.feed_forward.w2 --strengths 0 0.5 1 2
```

Без `--layers` проверяются все распознанные MLP-выходы, что требует существенно
больше проходов модели. `--steps` относится только к обучению весов через `run`.

Вмешательство добавляется только к последнему токену промпта в выбранном модуле,
одинаково для обоих кандидатов ответа. Веса не изменяются. На test сравниваются
нулевое вмешательство, выбранный вектор, случайное направление той же нормы,
противоположное направление и явное указание операции в промпте. Композиции
складывают выбранные векторы и не используются при извлечении или подборе.
Нормы случайных контролей совпадают по примитивам; норма их суммы может отличаться.

Артефакты: `vectors.safetensors`, `report.json`, `summary.md`. В отчёте сохраняются
все validation-оценки, выбранные параметры, отдельные ответы, правильность всей
ситуации и пары, согласованность механизма лампы, сохранение ответов и откат.
Совпадение реле и лампы само по себе не означает правильного вмешательства:
пара `(1,1)` согласованна, но неверна для `relay=0`.

Этот первый эксперимент не исключает примеси формулировки инструкции или
склонности отвечать определённой цифрой. Случайный и противоположный контроль
не доказывают семантическую специфичность. Перенос направления в изменения
весов имеет смысл после успешной проверки управления активациями.

### Постоянный сдвиг против оператора по состоянию

```console
semop compare --layers model.layers.8.feed_forward.w2 --strengths 0 0.5 1 2
```

Все методы получают одинаковые 40 train-пар активаций «с вмешательством / без»:

- `constant`: средняя разность активаций, как в `steer`.
- `conditional`: средняя разность плюс регуляризованная линейная поправка,
  зависящая от текущего состояния. Ridge-регрессия решается точно в пространстве
  40 примеров; матрица hidden_dim × hidden_dim не создаётся.
- `shuffled`: тот же условный оператор, но соответствия состояний и целевых
  изменений случайно перемешаны. Контроль получает свою равную сетку валидации.

Один оператор обучается на каждый примитив. Центрирование и масштаб признаков
вычисляются только на train. Регуляризация фиксирована: `--ridge 0.1`.
Валидация выбирает слой и силу отдельно для каждого метода; нулевое вмешательство
обязательно включено. Бюджет данных и сетка выбора совпадают, число параметров
у условного оператора больше. `--steps` здесь не используется.

Без `--layers` используется один модуль из профиля (либо автоматический средний
MLP-выход). Можно передать несколько путей через пробел для одинакового поиска
слоя всеми методами. Каждому тестовому вопросу соответствует собственный сдвиг,
вычисленный по активации его исходного промпта, без ответа и без инструкции
вмешательства. Оба кандидата ответа получают один и тот же сдвиг.

Композиция складывает сдвиги, предсказанные по исходным состояниям. Это пока
не последовательное применение операторов к результатам друг друга. Исходные
веса не изменяются. Проверяется точность всей ситуации и пары реле–лампа,
сохранение остальных ответов и точность отката.

Папка `runs/*-compare-*` содержит `report.json`, `summary.md` и
`transitions.safetensors` с обученными параметрами. В отчёте также есть train-MSE
восстановления сдвигов и все оценки валидации. Малый train-MSE не доказывает
перенос или причинное рассуждение; даже успешное сравнение потребует повторения
на новых шаблонах и seed. Целевые активации получены из текстовых инструкций,
поэтому могут включать особенности формулировки и ошибочные ответы модели.

### PCA-подпространство изменений

```console
semop compare --layers model.layers.8.feed_forward.w2 --strengths 0 0.5 1 2 --pca-components 2 4 8
```

К сравнению добавляются `pca_2`, `pca_4`, `pca_8` и `pca_selected`. PCA строится
через SVD только по центрированным **train-разностям** активаций. Средний сдвиг
сохраняется отдельно. Условная ridge-модель предсказывает коэффициенты в этом
базисе, затем восстанавливает сдвиг в исходной размерности. Число компонент
ограничивается численным рангом данных; при нулевой дисперсии остаётся среднее.

Для каждого фиксированного ранга сетка слоёв и сил та же, что у контрольных
методов. `pca_selected` выбирает ранг по валидации отдельно для каждого примитива;
при равных метриках предпочитает меньший запрошенный ранг. Его суммарный бюджет
поиска больше, чем у отдельного метода. Смотрите также отдельные ранги, чтобы
отделить эффект ограничения размерности от дополнительного подбора.
В отчёт включены фактический ранг, объяснённая доля train-дисперсии и ошибка
предсказания изменений. Дисперсия не используется как критерий качества ответов.

С этим флагом дополнительно выполняется **привилегированный диагностический
контроль** `oracle_diagnostics`: для каждого вопроса берётся настоящий MLP-выход
из его промпта с явным вмешательством и заменяет выход на последнем токене
исходного промпта. Это точная подстановка в одной точке, а не перенос всей
истории или состояния модели. Контроль использует подсказку о вмешательстве,
поэтому не считается результатом обобщения. Он выполняется после выбора
параметров, отдельно для каждого слоя и сценария, и не участвует в обучении
или выборе ранга. Для композиции донор содержит обе инструкции.

`transitions.safetensors` сохраняет также PCA-базисы; `summary.md` выводит
диагностический контроль отдельно от обученных методов. Веса модели не меняются.

### Локализация одиночных и совместных вмешательств

```console
semop localize --layer-sets 8 6,7,8 2,5,8 --windows 1 4 --boundaries prompt decision
```

Индексы слоёв считаются с нуля. Каждый аргумент `--layer-sets` задаёт отдельный
набор: одиночный слой 8, группа 6/7/8, группа 2/5/8. Для каждого набора отдельно
проверяются MLP-выходы и полные выходы decoder-блоков. Донорские активации
снимаются с неизменённого прохода, затем одновременно устанавливаются hooks
на весь выбранный набор в проходе исходного промпта.

Без ограничений `semop localize` проверяет все одиночные слои, все соседние
тройки и набор всех слоёв, окна 1 и 4, обе границы. Это не полный перебор
подмножеств; полный запуск существенно дороже короткой команды выше.

**Граница ответа существенна.** В токенизаторе используемой LFM2 кандидаты
`" 0"` и `" 1"` содержат общий токен пробела перед цифрой. `prompt` вмешивается
до этого пробела; `decision` — после общего префикса, перед различающим токеном.
Префикс вычисляется по токенизатору, различающиеся токены ответа никогда не
попадают в донорский проход. Если общий префикс пуст, границы совпадают.

Окно выравнивается по одинаковому суффиксу токенов до выбранной границы.
Если запрошенное окно длиннее общего суффикса, используется доступная длина,
которая записывается в отчёт. Это позиционное выравнивание, не семантическое
сопоставление произвольных участков текста.

Набор, тип выхода, окно и граница выбираются только по validation. На test
выбранный набор сравнивается с каждым его одиночным слоем, самым глубоким
слоем отдельно, исходной моделью и явной инструкцией. Подстановка собственных
активаций проверяет корректность механизма; после снятия hooks проверяется
откат. В `report.json` сохраняются все validation-кандидаты, выбранные параметры,
токенизация ответов и тестовые ответы. Артефакты: `runs/*-localize-*/report.json`
и `summary.md`.

Это привилегированный диагностический перенос готового состояния из промпта
с вмешательством, а не обученный оператор. Замена полного выхода позднего блока
может перезаписать эффект ранних слоёв, поэтому успех набора не доказывает их
совместную необходимость. На этом этапе локализуются три примитивных операции;
композиции обученных операторов не оцениваются.

### Обученные операторы в найденном блоке

После локализации можно обучить те же методы на полном выходе блока 12
непосредственно перед цифрой ответа:

```console
semop compare --site-kind block --layers 12 --boundary decision --pca-components 2 4 8 --strengths 0 0.5 1 2 --preservation-weight 1
```

Нумерация с нуля; вместо `12` допустим полный путь `model.layers.12`.
`constant`, `conditional`, `shuffled` и PCA обучаются только на train-парах
нейтрального и донорского состояния в указанной точке. Окно — один токен.
В режиме `decision` к промпту добавляется только общий префикс кандидатов
` 0` / ` 1` (для LFM2.5 это пробел), без различающей цифры. На тесте обученный
оператор получает только нейтральное состояние вопроса.

`--preservation-weight` задаёт **штраф при выборе силы на валидации**.
Первый критерий: доля полностью правильных миров минус вес штрафа,
умноженный на долю новых ошибок среди ранее правильных ответов об источнике,
выключателе и флаге. Затем сравниваются правильность пары реле–лампа и общая
точность. При отсутствии ранее правильных защищённых ответов штраф равен нулю;
число таких ответов всегда записывается. Нулевая сила включена в сетку.
Это мягкий штраф, а не гарантия сохранения инвариантов. Обучение ridge по
донорским разностям остаётся прежним; штраф не входит в его функцию потерь.

`report.json` содержит исходные и штрафованные оценки всех validation-кандидатов,
`protected_damage` с разбивкой по узлам для каждого тестового метода,
точное место подстановки, проверку собственного состояния и откат.
`summary.md` отдельно показывает повреждения. Параметры и метаданные позиции
сохраняются в `transitions.safetensors`. В этом режиме точная донорская
подстановка выполняется даже без PCA, после выбора операторов.

Прежний запуск без новых флагов сохраняет MLP-выход последнего токена промпта
и нулевой штраф. Для сравнения влияния штрафа повторите команду с
`--preservation-weight 0`. Выбор блока 12 опирался на предыдущие тестовые
результаты: этот опыт исследовательский; подтверждение потребует новых данных.

### LoReFT с сохранением поведения и новыми причинными схемами

Перед обучением проверьте базовые ответы модели:

```console
semop diagnose --max-new-tokens 16
```

Команда использует текущий профиль и `.env`, ничего не обучает и сравнивает:

- прежнее ранжирование продолжений `" 0"` / `" 1"`;
- ранжирование `"0"` / `"1"` без начального пробела;
- свободную greedy-генерацию из того же chat-промпта, без заданной цифры или пробела.

Проверяются три формулировки (`default`, `verbal`, `query_first`) для всех восьми
состояний: AND/copy на train и validation, все восемь схем на test. Всего 1272
вопроса. Генерация использует argmax по полному словарю, без sampling, KV cache и
logits processors; это диагностический декодер, его настройки могут отличаться
от LM Studio. Бюджет `--max-new-tokens` по умолчанию 16. Промпт и бюджет должны
помещаться в `max_length`, молчаливого обрезания нет.

В `runs/*-diagnose-*/report.json` сохраняются исходные промпты, текст и токены
генерации, причина остановки, обе токенизации кандидатов, расхождения методов,
число ответов 0/1 и ошибки отдельно по правильной метке, узлу и формулировке.
Все формулировки и splits используют одно требование:
`Reply with exactly one digit: 0 or 1. Do not add words, punctuation, or an explanation.`
Ответ генератора считается бинарным только после остановки по EOS, если весь
декодированный текст после удаления окружающих пробелов — `0` или `1`;
специальные токены не декодируются. `generation_status` различает `binary`,
`format_error` и `incomplete`. Достижение лимита токенов всегда считается
незавершённым ответом, даже если успела появиться одна цифра. Незавершённые
объяснения и законченные ответы неверного формата имеют `prediction: null` и
раздельные счётчики `incomplete` / `format_errors`, оставаясь ошибками в общем
знаменателе. `summary.md` содержит сводную таблицу.

Для отдельной проверки понимания вмешательства:

```console
semop diagnose --intervention-audit --max-new-tokens 16
```

Этот режим сравнивает исходный промпт, прежнее `Override ... force relay=...`
и **замену ровно нужного уравнения**. Например, после `do(relay=1)` печатается
`relay = 1; lamp = NOT relay`, без прежнего уравнения реле. Прямое `do(lamp=1)`
заменяет только уравнение лампы; источник, выключатель, флаг и остальные
уравнения сохраняются. Для каждого режима сравниваются bare-кандидаты и
свободная генерация. Все режимы оцениваются относительно одной символической
цели после вмешательства. Проверяются восемь схем, восемь состояний, три
операции, одна `default`-формулировка. Исходная генерация переиспользуется;
всего 2408 отдельных запросов генерации. Это отдельный отчёт
`runs/*-intervention-audit-*`, без обучения и выбора операторов. В нём есть
точность реле и лампы отдельно, все сырые промпты, ошибки формата и повреждения.

После диагностики запустите обучение v4:

```console
semop reft --layers 8 12 15 --rank 4 --steps 80 --learning-rate 0.003 --locality-weight 1 --preservation-weight 1 --pca-components 2 4 8 --max-new-tokens 16 --loss-mode full_vocab --train-schemes and_copy and_inverted
```

Используются текущие `.env` и профиль модели. В `loreft_causal_suite_v4` по
умолчанию включены `--loss-mode full_vocab` и обе обучающие схемы COPY/NOT.
Требуемый ответ остаётся **`"0"` / `"1"` без пробела**, затем EOS.
Вмешательство происходит на выходе **последнего токена исходного chat-промпта**.
Кандидаты ответа не входят в захватываемое состояние. Оригинальные веса
заморожены; обучаются только параметры вмешательства.

`--layers` теперь принимает список проверяемых decoder-блоков, с нуля.
До обучения `reft` повторно проверяет каждый блок на validation выбранных COPY/NOT:
точные донорские подстановки для трёх операций и подстановку собственного
состояния. Выбирается один общий блок по среднему штрафованному критерию трёх
операций: целостность всех узлов минус повреждения источника/выключателя/флага,
затем правильность пары реле–лампа и общая точность. При равенстве выбирается
меньший индекс. После этого выбор силы LoReFT и остальных методов остаётся
отдельным этапом. Новые тестовые схемы не участвуют в обоих выборах.

При локализации захват выполняется в том же проходе оценки кандидатов, что
и подстановка: совпадают порядок строк, размер батча, дополнение и длина
последовательности для self-patch. Позиция захвата остаётся перед ответом;
каузальная маска исключает влияние последующих токенов кандидата. Состояния
обеих строк кандидатов сохраняются отдельно. Это устраняет несовпадение
вычислительных условий в прежней проверке (захват двух промптов против оценки
четырёх строк с кандидатами), существенное при численном округлении. Допуск
`atol=rtol=1e-5` сохранён. При сбое выводятся блок, максимальное расхождение,
число изменившихся ответов, конечность значений, устройство и dtype.

Раздел `localization` сохраняет все оценки, `selected_layer`, проверку
собственного состояния и `beats_no_patch`. Если ни одна донорская подстановка
не улучшила исходный результат, этот факт явно отмечается; исследовательское
обучение продолжается в лучшем из проверенных блоков. Донорская локализация
не гарантирует, что именно этот блок лучше всего подходит обученному LoReFT.
Без `--layers` проверяется только блок 12; с `--layers 12` заново проверяется
та же единственная позиция. Наборы блоков одновременно здесь не обучаются.

LoReFT реализует уравнение 2 из [Wu et al., 2024](https://arxiv.org/abs/2404.03592):
`h' = h + R.T @ (W @ h + b - R @ h)`, где строки `R` ортонормированы.
Наша реализация использует дифференцируемый reduced QR и инициализацию
тождественным преобразованием (`W=R`, `b=0`). Она работает на существующих
PyTorch hooks, включая нашу загрузку LFM2.5 GGUF; установка `pyreft` не требуется.
Это воспроизведение формы оператора, **не** результатов бенчмарков статьи.

В каждом запуске сравниваются:

- `loreft_task`: обучение по правильным ответам затронутых переменных;
- `loreft_locality`: та же инициализация, выборка и число шагов плюс forward KL
  на незатронутых вопросах;
- `constant`, `ridge`, `pca_K`: прежние методы восстановления донорской разности;
- исходная модель, явная инструкция и отдельная точная донорская подстановка.

Locality-подход мотивирован [MEND](https://arxiv.org/abs/2110.11309), но здесь
обучается оператор активаций, а не редактор весов MEND. По умолчанию CE и KL
вычисляются **по полному словарю**. CE охватывает все токены правильной цифры
и один EOS. Если настроено несколько стоп-токенов, обучение использует первый,
генерация принимает любой из них. При отсутствии EOS обучение завершается
понятной ошибкой. Все токены многотокенной цифры учитываются.

Для защищённого вопроса исходное и изменённое распределения сравниваются
на одинаковой истории: исходный промпт и teacher-forced правильный естественный
ответ. KL включает предсказание цифры и EOS, усредняется по токенам вопроса.
Это ограничение на проверенных историях; произвольные продолжения оно не
ограничивает. Полные исходные log probabilities кешируются в RAM на CPU.
При 240 вопросах, двух токенах ответа и словаре 65536 кеш занимает около 120 MiB.
Место вмешательства остаётся фиксированным: у последнего блока изменение
последнего токена промпта не влияет на более поздние teacher-forced позиции.
Поэтому наличие EOS в loss само по себе не гарантирует завершённую генерацию.

`--loss-mode binary` сохраняет прежнюю CE/KL по двум кандидатам для абляции
на **тех же** схемах и промптах. Выбор alpha и таблицы candidate-scoring пока
используют bare-ранжирование `0/1` без EOS; итоговая свободная генерация отдельно
проверяет весь ответ и остановку. `loss_mode`, токены завершения и схемы обучения
записываются в отчёт. Смена loss не воспроизводит старый v3: формулировка
вмешательства и выборка тоже изменились.
Для вмешательства в реле целевые переменные — реле и его потомки; остальные
ответы сохраняются. Для вмешательства только в лампу сохраняется также реле.
Маски определяются внешней причинной моделью только при обучении; оператор
на тесте получает скрытый вектор без этих масок и без донорского прохода.
Начиная с `loreft_causal_suite_v2`, один шаг содержит **все пять вопросов об одном
состоянии и одной формулировке**. Схемы чередуются, внутри каждой чередуются
состояния с изменяемым и сохраняющимся ответом. По умолчанию train содержит
240 вопросов: 2 схемы × 8 состояний × 5 узлов × 3 формулировки.
В штатном запуске на 80 шагов покрываются все вопросы; фактическое покрытие
всегда записывается в `training`. Оба LoReFT-варианта используют одинаковый
порядок состояний, инициализацию и бюджет.

Вопросы проходят сеть порциями по два с накоплением градиента. CE нормируется
по всем затронутым вопросам состояния, KL — по всем незатронутым; шаг Adam
выполняется после полного состояния. Благодаря этому небольшой остаточный
микробатч не получает лишний вес, а графы всех пяти вопросов не хранятся вместе.
Журнал каждого шага содержит `by_node`: целевую CE и locality KL отдельно по
узлам. В режиме full_vocab также записывается совпадение наиболее вероятного
первого токена с базовой моделью на защищённых вопросах; binary сохраняет
прежние счётчики повреждения кандидатов. Значения относятся к состоянию до обновления.

`--locality-weight` влияет на **обучение**, `--preservation-weight` — на
**выбор блока и силы по валидации**. Сетка сил одинакова у всех методов и включает 0
(по умолчанию `0 0.5 1 2`). PCA-ранги записываются отдельно, без выбора лучшего
по тесту. Ridge сохраняет коэффициент 0.1. Сравнение методов не уравнивает
их объём параметров и вид обучения: LoReFT использует правильные ответы,
ridge/PCA — состояния промптов с инструкцией.

Обучение и валидация используют `and_copy` и `and_inverted`, с разными шаблонами
и именами. `--train-schemes and_copy` позволяет отдельно проверить вклад NOT.
Другие схемы CLI не разрешает включать в обучение.
Валидация и основной тест сохраняют отдельный `default`-шаблон своего split;
дополнительные обучающие формулировки не добавляются в выбор силы.
Validation содержит 80 вопросов. Шесть остальных механизмов/структур доступны
только в итоговом тесте. `test_groups` явно разделяет знакомые механизмы и
отложенные механизмы/топологии:

| Набор | Уравнения | Что проверяет |
|---|---|---|
| `and_copy` | relay = source AND switch; lamp = relay | Новые имена/шаблон, прежняя схема |
| `or_copy` | relay = source OR switch; lamp = relay | Другой механизм реле |
| `and_gated` | relay = source AND switch; lamp = relay AND flag | Новая зависимость лампы |
| `and_chain` | relay = source AND switch; bridge = relay; lamp = bridge | Более длинная цепочка; вопросы также о bridge |
| `and_inverted` | relay = source AND switch; lamp = NOT relay | Второй обучающий механизм с противоположным последствием |
| `and_xor` | relay = source AND switch; lamp = relay XOR flag | При relay=0 лампа равна flag; при relay=1 — NOT flag |
| `and_inverted_chain` | relay = source AND switch; bridge = NOT relay; lamp = bridge | Новая цепочка с инверсией |
| `and_xor_chain` | relay = source AND switch; bridge = relay XOR flag; lamp = bridge | Новая цепочка с XOR |

Во всех схемах источник, выключатель и флаг сохраняют свои значения.
Прямое вмешательство `lamp=1` по-прежнему переопределяет правило лампы.
Такие тесты различают перенос причинной зависимости и общее смещение ответов
в сторону одной цифры. Новые цепочки и XOR оператор при обучении не видит.

Композиции применяют преобразования последовательно к одному скрытому вектору,
в обоих порядках. Повторного прохода сети между операторами нет. Разрешение
конфликтующих назначений в `revision` по-прежнему задаётся внешним правилом
«последняя запись побеждает». Это не обученное обнаружение противоречия.

Результаты: `runs/*-reft-*/report.json`, `summary.md`, `operators.safetensors`.
Отчёт содержит обучение, выбор силы, ответы по каждому узлу и схеме, повреждения,
композиции, донорский контроль и откат. Отдельный раздел
**`fixed_strength_diagnostics`** всегда оценивает оба LoReFT-варианта при
заранее заданном `alpha: 1.0` для трёх примитивных операций на полном train,
validation и каждой тестовой схеме. Это выполняется и при `--strengths 0`;
фиксированные оценки не участвуют в выборе силы. Внутри есть исходная модель,
ошибки отдельно для меток 0/1, разбивка по узлам/формулировкам и сырые ответы.
В `summary.md` для них предусмотрена отдельная таблица, включая повреждения
источника, выключателя и флага. `test` по-прежнему содержит результаты с силой,
выбранной на validation; его композиции используют только выбранные силы.

Раздел **`greedy_test`** проверяет свободную генерацию на каждой тестовой схеме
для трёх примитивных операций. Сравниваются исходная модель, явная инструкция,
оба варианта LoReFT с выбранной силой и при `alpha=1`. Повторные вычисления для
одинаковых сил переиспользуются; нулевая сила использует исходную генерацию.
Генератор выбирает токены из полного словаря без принудительного префикса.
На каждом проходе без KV cache оператор применяется к той же позиции исходного
промпта, **не перемещаясь на сгенерированные токены**. Поэтому позиция и
преобразование согласованы с обучением и оценкой кандидатов.

Сохраняются исходные промпты, текст и токены генерации, статус завершения,
правильность всех узлов, повреждения источника/выключателя/флага и совпадение с
ранжированием кандидатов. Повреждения в этом разделе отсчитываются от правильных
**исходных генераций**, а не от оценок кандидатов. Сравнение с кандидатами имеет
отдельный знаменатель по завершённым бинарным генерациям. Все невалидные ответы
остаются в общей точности. Генерация композиций пока не измеряется: их результаты
относятся только к ранжированию кандидатов. Дополнительная генерация увеличивает
время запуска; `--max-new-tokens` управляет её бюджетом.

Объём обучающих данных и число проходов за шаг увеличились относительно v1;
одинаковые `--steps 80` не означают одинаковый вычислительный бюджет. В v4
добавились NOT в обучение, замена уравнений и полная функция потерь; в v3
менялись протокол ответа и инструкции. Старые операторы нельзя
считать проверенными в новой позиции. Шаблоны этой серии отличаются от старого
`compare`: сопоставляйте методы внутри одного запуска, а не только проценты
с прежними архивами. Прежние `run`/`steer`/`compare`/`localize` сохраняют свой
протокол с пробелом. `answer_protocol` записывается в JSON и метаданные safetensors.

### Отдельная диагностика DAS

```console
semop das --layers 12 --rank 4 --steps 80 --learning-rate 0.003
```

`das_causal_alignment_v2` также использует общий строгий формат и bare-кандидаты
на последнем токене промпта. `--layers` здесь принимает один индекс блока;
автоматический выбор позиции и свободная генерация относятся к команде `reft`.
Тестовые схемы включают инверсию и XOR. Предыдущие отчёты DAS использовали другой
протокол ответа, поэтому прямое сравнение процентов между версиями ограничено.

Реализуется низкоранговая форма distributed interchange intervention:
`h' = h + R.T @ (R @ h_source - R @ h)`;
основание — [Geiger et al., 2024](https://proceedings.mlr.press/v236/geiger24a.html)
и уравнение 1 работы LoReFT. Для реле и лампы обучается по одному подпространству,
общему для значений 0 и 1, без обучения основной модели.

Донор — **другой нейтральный мир** с той же ролью вопроса. В его промпте нет
инструкции вмешательства и нет цифры ответа. Цель — ответ причинной схемы
получателя после `do(variable = source.variable)`. Остальные значения донора
переносить не нужно; правильный ответ получателя может отличаться от ответа
донора. В каждом обучающем шаге есть случай изменения ответа и случай его
сохранения. Обучение фиксировано по шагам; валидация только записывается.

На валидации и каждой тестовой схеме проверяются все упорядоченные пары
8×8 миров и все роли вопросов — 320 примеров на переменную, 384 в длинной цепи.
Контроли: исходная модель, исходное случайное подпространство, полная подстановка
донора. Записываются interchange intervention accuracy (IIA), изменяемые случаи,
целостность всех узлов, повреждения защищённых ответов и отдельное подмножество,
где оба естественных ответа — донора и получателя — правильны. Нулевой размер
этого подмножества обозначается `accuracy: null`.

Артефакты: `runs/*-das-*`. Здесь донор нужен и на тесте, поэтому результаты DAS
помечаются как диагностика и не смешиваются с результатами операторов LoReFT.
Позднее состояние зависит от вопроса и может кодировать готовый ответ: высокий
IIA сам по себе не доказывает локализацию промежуточной причинной переменной.
Пары миров коррелированы; это не сотни независимых наблюдений. Для выводов
потребуются дополнительные seed, задачи и точки вмешательства.
